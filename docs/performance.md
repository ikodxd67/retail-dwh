# Замеры и оптимизации

Все цифры сняты на стенде: Docker Desktop под Windows, VM с 8 ГБ памяти,
PostgreSQL 16 (shared_buffers 512MB), ClickHouse 24.8. Данные: 543 320
заказов, 1 449 859 строк заказов, история с 01.01.2025. Каждый запрос
выполнялся три раза подряд; указан разброс.

## 1. Эффект промо: составной индекс вместо индекса по товару

Запрос `sql/analytics/06_promo_uplift.sql` для каждой пары «товар × неделя
акции» считает продажи за 8 недель до неё (LATERAL). С индексом только по
`product_sk` планировщик доставал всю историю товара во всех 37 секциях и
отбрасывал лишние даты уже после чтения.

Индекс `(product_sk, order_ts) INCLUDE (qty, order_status, promo_campaign_id)`
превращает это в диапазонный поиск, а INCLUDE даёт index-only scan без
обращения к таблице (после VACUUM, когда карта видимости заполнена).

| | Execution Time | shared buffers |
|---|---|---|
| индекс `(product_sk)` | 4 611 – 5 751 мс | 1 914 649 |
| индекс `(product_sk, order_ts) INCLUDE (...)` | 433 – 474 мс | 152 806 |

Ускорение примерно в 11 раз, страниц читается в 12,5 раз меньше. Старый
индекс удалён: всё, что он умел, новый умеет тоже (`product_sk` — первая
колонка). Миграция `sql/dwh/006_tz_and_product_index.sql`.

Первый замер «до» дал 6,85 с, но он был снят до VACUUM, а в таких
условиях сравнение нечестное. В таблице повторный замер: оба варианта
после ANALYZE, одна и та же сессия.

## 2. Загрузка сателлитов: LATERAL вместо DISTINCT ON

Чтобы понять, изменилась ли запись, загрузчик vault сравнивает hashdiff
новой версии с последней версией ключа в сателлите. Два способа найти
последнюю версию для 3 000 ключей в `sat_order_line_erp` (1,45 млн строк):

| | Execution Time |
|---|---|
| `DISTINCT ON (hk) ... ORDER BY hk, load_dts DESC` по всему сателлиту | 474 – 963 мс |
| `LEFT JOIN LATERAL (... WHERE hk = k.hk ORDER BY load_dts DESC LIMIT 1)` | 2,9 – 17,8 мс |

DISTINCT ON сортирует весь сателлит ради 3 000 ключей, а LATERAL делает
3 000 точечных спусков по первичному ключу `(hk, load_dts)`. Разница
растёт вместе с сателлитом, поэтому в `vault/render.py` сгенерирован
LATERAL.

## 3. Где считать агрегаты: PostgreSQL или ClickHouse

Выручка, маржа и число заказов по месяцам × группам товаров × городам,
вся история:

| | время | на диске |
|---|---|---|
| PostgreSQL, звезда (`fact_sales` + измерения) | 4 242 – 4 442 мс | 496 МБ (с индексами) |
| ClickHouse, `retail.sales_wide` | 44 – 119 мс | 58 МБ сжато (206 МБ без сжатия) |

Поэтому витрина продаж публикуется в ClickHouse, а PostgreSQL остаётся
источником правды: там MERGE, SCD2, ссылочная целостность и сверки. BI
и ad-hoc аналитика идут в ClickHouse.

## 4. Полная сборка с нуля

| шаг | время |
|---|---|
| загрузка stg: заказы из Oracle (543 320 строк) | 3 с |
| загрузка stg: строки заказов из Oracle (1 449 859) | 9 с |
| загрузка stg: 45 файлов остатков CSV.gz (2 015 767 строк) | 23 с |
| raw_vault, все партии | 128 с |
| витрины, полная пересборка | 156 с (факт продаж 95 с, остатки 58 с) |
| публикация 21 месяца в ClickHouse | ~12 с |

Инкрементальный прогон `dwh_build` после получасовой загрузки занимает
10–20 секунд (по журналу запусков Airflow).

Как ускоряли сборку факта. Закупочная цена и курс на дату заказа ищутся
не коррелированным подзапросом на каждую из 1,45 млн строк. Сначала один
раз строятся интервалы действия цены и курса: `lead()` по снимкам каталога
и датам курсов даёт `valid_from/valid_to`. Потом с ними соединяются по
диапазону (`sql/marts/40_fact_sales.sql`).
