# Разбор проблемы с качеством данных

Работай через MCP-сервер `retail-dwh`. Ничего не исправляй в данных сам:
результат разбора — диагноз с доказательствами и предложение.

## 1. Что именно упало

- `data_quality(hours=24)` — проваленные проверки: таблица, имя, наблюдаемое
  значение и порог.
- Текст проверки — в `catalog/dq_marts.yml` (витрины) или в `checks`
  пайплайна (`pipelines/<имя>.yml`, если таблица stg).

## 2. Где началось

- `describe_dataset(<таблица>)` → `upstream`. Иди вверх по цепочке, пока не
  найдёшь слой, где данные уже неверны.
- `pipeline_status()` — есть ли партии `rejected`, `failed`, застрявшие
  `waiting_for_vault`, давно не двигавшийся водяной знак.
- `batch_details(<id>)` для подозрительной партии: окно водяного знака, число
  строк, текст ошибки.

## 3. Проверить гипотезу данными

Короткие запросы через `run_sql`, от общего к частному. Например, для
`lines_match_vault`:

```sql
SELECT date_trunc('day', order_ts) AS day, count(*)
FROM dwh.marts.fact_sales
WHERE order_ts > current_timestamp - INTERVAL '3' DAY
GROUP BY 1 ORDER BY 1
```

Сравни с источником по тем же дням. Если расходится один день — ищи партию
за этот день, если все — логику сборки.

Типовые причины:
| Симптом | Частая причина |
|---|---|
| `customers_missing_in_crm_pct` растёт | CRM-пайплайн стоит, заказы приходят раньше клиентов (ключ -2 исправится сам после загрузки CRM) |
| `lines_without_cost_pct` растёт | в каталоге нет закупочной цены или нет курса валюты на дату |
| `freshness_hours` | остановлен ERP-пайплайн или `dwh_build`; смотри `pipeline_status` |
| партия `rejected` | источник прислал дубли или NULL в ключе; смотри `batch_details` |

## 4. Отчёт

Коротко и по фактам: что упало, с какого момента, на каком слое началось,
доказательство (запрос и цифры), что предлагаешь. Если партию после
исправления источника можно пропустить в vault: `retail-dwh batch release <id>` —
но это решение человека, не твоё.

Не пиши догадок как фактов. Если проверить гипотезу нечем, так и скажи.
